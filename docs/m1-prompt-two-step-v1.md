# M1 两步示例 prompt 对照：开发结果未在预留题复现

1. **Outcome.** 在固定 M0 最终模型上，仅将 system prompt 中的 `2 + 3` 示例换成一个两步算术示例。100 道开发题的严格正确数从 3 增至 7；预先保留的 200 道确认题却从 13 降至 11。因此没有证据把该变体称为稳定的准确率改进。
2. **Before.** M0 原有固定内部验证为 9/200 → 9/200。后续对训练分区 100 题的[答案数值审计](m0-answer-audit-v1.md)显示，51 条正常结束但缺少最终行的回答里，15 条可提取数值与标答一致、32 条不同。这促使我们检验更具体的算术示例是否同时改善解题与答案格式。
3. **Why (Inferred).** 用户选择先做质量实验，再比较 rollout 后端。这里使用推理阶段的 prompt 改动作为最小干预，以免把模型训练、采样后端和提示词效果混在一起。
4. **Core intuition.** 同一权重、同一题序、同一 greedy 解码，只替换示例文本。如果示例真有稳定帮助，应在开发题和预留题上看到方向一致的严格正确数变化；任何格式改善都需要与数值正确分开检查。
5. **Flow.** [实验规格](../configs/m1-prompt-two-step.yaml)把基线的“2 + 3 = 5”换成“3 盒、每盒 4 个苹果，卖出 5 个，剩 7 个”的两步示例；基础指令及示例后的句子保持相同。预留题 `train/07310` 的基线回答已写出 `95`，却没有 `####`；变体以 `#### 95` 结束，严格 reward 从 0 变 1。另一题 `train/03616` 的基线以 `#### 6` 结束，变体把 `#### 6` 放在句中，严格 reward 从 1 变 0。
6. **Explained change.** [开发脚本](../scripts/compare_prompt_quality.py)从先前未扫描、未审计的训练分区题中，按固定 SHA-256 排名预先划出 100 道开发题和 200 道预留题；它绑定原 M0 checkpoint 的校验值，加载原始 pinned tokenizer，用相同 greedy 设置生成两组逐题记录。[确认脚本](../scripts/confirm_prompt_quality.py)校验开发 manifest 中预留 ID 与现有配置一致，然后只对这些 ID 做一次相同对照。两份脚本只调用 `evaluate_model()`；没有 optimizer 或新参数更新。
7. **Invariants and boundaries.** 两组都用 `step-000002` 权重、相同 chat template、128-token 上限、严格 `#### <number>` verifier。前次诊断或扫描过的 226 个训练题 ID 被排除；新开发题、预留题及 M0 的 200 道固定验证题互不重叠。这里只能比较**这个 checkpoint 上的两个具体 prompt**；示例的文字与长度一起变化，不能把观察结果单独归因于“两步推理”。两批题来自 GSM8K 原 train 分区，不是官方 test，也不是新的模型泛化基准。
8. **Failure and recovery.** MPS 不可用、checkpoint 校验失败、数据 hash 不匹配或预留 ID 变化时，脚本在生成前报错。运行中断可留下 manifest 和部分 JSONL，但不会有 `status=completed` 的 summary；应在新输出目录重跑，不覆盖部分结果。预留题已用于一次确认，不能再用它调下一版 prompt 并称其仍未使用。
9. **Evidence.** 本机 MPS、float32、PyTorch 2.14.0、Transformers 4.57.6。原 checkpoint 的 12 个文件通过 SHA-256 校验。独立复核两批各两份 JSONL 的题序、严格 verifier、汇总和配对计数均一致。原始文件见[开发 manifest 与结果](../results/m1/prompt-two-step-v1/summary.json)、[预留确认 manifest 与结果](../results/m1/prompt-two-step-confirm-v1/summary.json)。完整仓库测试另行记录在执行日志。
10. **Comprehension check.** 见下方五个问题。预留集的原 prompt 严格正确 13/200，变体 11/200，因此本变体不进入后续训练配置。缺少最终行从 174 降至 154、截断从 58 降至 44，只支持“在这些题上输出形态改变”的结论，不支持准确率提高。

| 题集 | 原 prompt 严格正确 | 两步示例严格正确 | 变对 / 变错 | 缺少最终行，原 → 变体 | 截断，原 → 变体 |
|---|---:|---:|---:|---:|---:|
| 开发 100 题 | 3 | 7 | 7 / 3 | 84 → 76 | 29 → 17 |
| 预留确认 200 题 | 13 | 11 | 10 / 12 | 174 → 154 | 58 → 44 |

## Questions

1. 两个 prompt 对照共用哪些模型和评估条件？
2. 100 道开发题和 200 道预留题是怎样选择并隔离的？
3. 为什么开发题 3→7 不能单独作为“prompt 有效”的结论？
4. 中断后若只有一份 JSONL、没有完成 summary，该怎样处理？
5. 预留题上缺少最终行减少，为什么仍不能说解题能力提高？

## Answers

1. 同一 M0 最终 checkpoint、原始 pinned tokenizer、chat template、题序、greedy 解码、128-token 上限和严格 verifier；只替换 system prompt 的示例文本。
2. 从 GSM8K train 的 M0 非验证分区，先排除已扫描或审计的 226 个 ID，再用固定盐值的 SHA-256 排名选前 100 个为开发、后 200 个为预留；确认脚本复算并检查 ID。
3. 同题有 7 个新正确、3 个失去正确，没有一题两组都正确；预留题方向反转为 13→11，说明开发结果未复现。
4. 使用新的输出目录重跑，并将只有部分行、无完成 summary 的目录标为不完整；不要把它当作成功结果。
5. 严格正确数实际减少，且变体的有效格式但数值错误回答更多；输出结构和算术数值必须分开看。

## Open questions

- 下一轮质量实验应检验模型数值能力或训练数据/方法；需要重新划出未用于方案选择的题，不能循环调这 200 道确认题。
- 若未来主张系统性能，仍需单独测 rollout 吞吐、时间和内存；本实验没有记录可比较的性能数据。
