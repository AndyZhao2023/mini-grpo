# M2 固定预算采样对照：当前最短题优先得到更多混合奖励组

1. **Outcome.** 固定 M0 最终模型与原提示词，每种选题方式各采样 64 道未使用训练题、每题 4 个回答。最短题优先有 **11/64** 组混合奖励，哈希随机题有 **2/64**。这批题上，当前最短题优先的方式提供更多可用于组内优势计算的题组；没有做任何参数更新，也没有测到 held-out 准确率变化。
2. **Before.** M0 每次扫描在第一组混合奖励处停止，两次更新的扫描均为 7 组中 1 组混合奖励；它不能估计固定预算内不同选题方式的混合组比例。[M0 报告](m0-final-report.md)与[扫描代码](../scripts/find_trainable_group.py)记录了该行为。M1 的两步示例在预留题上没有提高严格正确数，故本实验保持原提示词。
3. **Why (Supplied).** 用户同意先比较训练信号密度，再决定是否进行更长训练；固定模型、prompt、`G`、reward 与组数预算，只改变选题方式。
4. **Core intuition.** 同题 4 个回答若奖励全相同，组内标准差为零，不能形成该题的相对优势。扫描满 64 题而不是遇到第一个混合组就停，才能在相同题数预算下比较两种选题方式。
5. **Flow.** 先排除以前扫描或评估过的 526 个训练 ID。`shortest` 按现有规则以题干词数、ID 排序取前 64；`hash_random` 从余下题目按固定盐值的 SHA-256 排名取前 64。对每道题以基础 seed 和 ID 派生固定种子，复用 `sample_group()` 生成 4 个回答，再用 `verify_group()` 给出严格 0/1 reward。例：最短题第 8 组 `train/00701` 的奖励为 `[0,0,0,1]`；哈希随机题第 12 组 `train/06394` 同样为 `[0,0,0,1]`。所有零奖励组也保留在逐组记录中。
6. **Explained change.** [实验规格](../configs/m2-sampling-order-v1.yaml)固定两个分支和各 64 组的预算。[脚本](../scripts/compare_sampling_order.py)先核对已完成的 M0 运行、最终 checkpoint 的公开 SHA-256 清单、固定版本数据和旧题排除清单，再加载原始 pinned tokenizer 与本地保留的 `step-000002` 权重。它将预选 ID 写入 [manifest](../results/m2/sampling-order-v1/manifest.json)，逐组写入[最短题](../results/m2/sampling-order-v1/shortest.jsonl)和[哈希随机题](../results/m2/sampling-order-v1/hash_random.jsonl)，最后写入[汇总](../results/m2/sampling-order-v1/summary.json)。脚本不创建 optimizer，不调用训练步骤。
7. **Invariants and boundaries.** 两组各 64 个互不重叠的原始 train ID，均与 M0 固定验证题、M1 开发和预留题及已扫描的训练题隔离；官方 test 未读取。两组使用相同权重、tokenizer、系统提示词、采样参数、`G=4`、256-token 上限和严格 verifier。哈希随机组平均题干为 44.1 词，最短题组为 19.4 词；这是选题策略造成的题目组成差异，不能把结果单独归因于“题目长度”。每组只用一个预定种子和 64 道题，结果不证明该排序普遍更优，更不证明训练后泛化收益。
8. **Failure and recovery.** MPS、checkpoint 哈希、数据哈希或旧实验 manifest 不匹配时，在采样前报错。输出目录不能已存在；中断后可能留下 manifest 和部分 JSONL，但没有 `status=completed` 的 summary，不能当作完整实验。应保留残件并换新目录重跑；本机 MPS 新运行未承诺字节级生成相同。
9. **Evidence.** 本机 MPS、float32、PyTorch 2.14.0、Transformers 4.57.6。79 项仓库测试通过；事后 12 个 checkpoint 文件的 SHA-256 全部通过。独立使用固定 GSM8K 标答与原 verifier 重算 512 条回答，检查 128 个 ID 均未使用且互不重叠，逐组混合标记及汇总吻合。结果见下表；耗时只覆盖逐组生成与评分，不含加载、数据或校验时间。
10. **Comprehension check.** 见下方五个问题。

| 指标 | 最短题优先 | 哈希随机 |
|---|---:|---:|
| 采样题组 / 回答 | 64 / 256 | 64 / 256 |
| 混合奖励组 | **11/64（17.2%）** | **2/64（3.1%）** |
| 严格正确回答 | 14/256 | 7/256 |
| 平均题干词数 | 19.4 | 44.1 |
| 实际生成 response token | 19,047 | 24,728 |
| 生成与评分耗时 | 155.6 秒 | 200.0 秒 |

## Questions

1. 为什么现有“找到第一组就停止”的扫描不能回答本实验的问题？
2. 一个 `[0,0,0,1]` 的题组为何可提供组内训练信号？
3. 两个分支固定了什么，唯一改变的是什么？
4. 如果运行中断、只留下一个分支的 JSONL 而无完成 summary，如何处理？
5. 11/64 对 2/64 是否足以决定“更长的 GRPO 训练会提升验证正确率”？

## Answers

1. 停止时间随遇到第一组混合奖励而变化，两组实际扫描题数不相同；本实验固定两组均扫描 64 题。
2. 组内奖励有差异，归一化后的优势有正负值；全 0 或全 1 则没有这个相对信号。
3. 固定 checkpoint、prompt、tokenizer、数据版本、每题 4 个回答、生成参数、reward 和题组预算；改变的是训练题的选择方式。
4. 标记为不完整，不把部分结果当作 64 组结论；保留残件，换新输出目录重跑。
5. 不足以。本实验只衡量固定权重上的 rollout 奖励密度。下一次训练仍需预定更新预算，并在未用于选方案的新 held-out 题上比较训练前后结果。

## Open questions

- 这次哈希随机分支在固定样本上更少产生混合组，当前没有依据替换最短题优先策略；其余选题方法和不同随机种子尚未比较。
- 更高的混合组比例是否能转化为 held-out 正确率提升，需要另做训练实验。训练 reward、扫描命中率和泛化效果必须分开报告。
